# Dynamic Pricing Engine

A Python project for experimenting with simulated dynamic pricing. It combines a FastAPI
prediction API, an XGBoost training pipeline, MLflow tracking, Kafka event examples, and
Evidently-based feature drift checks.

> **Data note:** Training targets are generated by `synthetic_price_formula()`; they are
> not historical customer prices. Model scores and drift examples therefore describe
> simulated data, not real-world pricing performance.

## Architecture

```text
Training:    synthetic data -> feature columns -> XGBoost -> MLflow metrics + model file
Prediction:  REST request -> FastAPI -> feature engineering -> model -> price response
Monitoring:  reference/current features -> Evidently drift report -> optional retraining
Streaming:   event generator -> Kafka producer -> four topics -> consumer buffers by city
Delivery:    GitHub Actions tests/trains -> (main push) Docker build/push -> Kubernetes
```

The streaming and REST paths are separate today: the Kafka consumer assembles and logs
complete records, but does not call the prediction API. The API logs predictions to SQLite.
There is no Prometheus `/metrics` endpoint.

## Repository

| Path | Purpose |
|---|---|
| `config.py` | Feature list, paths, Kafka/MLflow settings, and drift/retraining thresholds |
| `src/data_generator.py` | Generates simulated order, weather, traffic, and competitor events |
| `src/feature_engineering.py` | Converts input records into the seven model features |
| `src/kafka_producer.py`, `src/kafka_consumer.py` | Publishes events and buffers them by city |
| `app/main.py` | FastAPI `/health` and `/predict` endpoints; SQLite prediction logging |
| `pipeline/train_pipeline.py` | Generates 5,000 synthetic rows, trains XGBoost, logs metrics, saves model/reference features |
| `pipeline/retrain_pipeline.py` | Checks drift, trains a challenger, and promotes it only if MAE improves enough |
| `monitoring/drift_detector.py` | Compares recent feature data with the saved reference data using Evidently |
| `data/processed/` | Generated reference feature data for drift checks |
| `tests/` | Pytest coverage for API, feature engineering, Kafka assembly, drift, and retraining |
| `.github/workflows/ci-cd.yaml` | Tests, model training, conditional image build/push, and Kubernetes deployment |
| `Dockerfile`, `docker-compose.yml`, `k8s/` | API container, local Kafka stack, and Kubernetes manifests |
| `dvc.yaml`, `dvc.lock`, `dvc_SETUP.md` | Training stage and DVC data/model versioning notes |

## Workflow

1. Generate simulated events or training data.
2. Engineer seven features: `base_price`, `peak_hour`, `demand_supply_ratio`,
   `competitor_gap`, `weather_factor`, `traffic_factor`, and `time_of_day`.
3. Train XGBoost on a reproducible 80/20 split. MLflow records MAE, RMSE, and R²; the
   model and drift reference data are saved under `pipeline/models/` and `data/processed/`.
4. Serve predictions through FastAPI. Drift checks compare current features against the
   training reference; retraining uses the same test split for champion/challenger MAE.
5. GitHub Actions runs tests and training for pull requests and pushes to `main`. Docker
   build/push and Kubernetes deployment run only on pushes to `main` and need repository
   registry and Kubernetes secrets.

The default drift threshold is a `0.5` share of the seven features; batches under 100 rows
are skipped. A challenger must improve MAE by at least 1% before replacing the current
model. Retraining currently uses synthetic data too.

## Run Locally (Windows PowerShell)

From the repository root:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt

$env:PYTHONPATH = "$PWD;$PWD/src"
$env:MLFLOW_TRACKING_URI = "sqlite:///mlflow.db"
python pipeline/train_pipeline.py
```

Training creates `pipeline/models/latest_model.json`,
`data/processed/reference_data.csv`, and the local MLflow database. Keep the environment
variables set in the terminal used to launch the API:

```powershell
uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Open `http://127.0.0.1:8000/docs` for interactive API documentation. On macOS/Linux,
activate `.venv` with `source .venv/bin/activate` and set
`PYTHONPATH="$PWD:$PWD/src"` plus `MLFLOW_TRACKING_URI=sqlite:///mlflow.db`.

## Try a Prediction

With the API running, use PowerShell:

```powershell
$body = @{
  order = @{
    order_id = "demo-001"
    city = "Mumbai"
    timestamp = "2026-09-30T18:30:00+00:00"
    demand_units = 40
    supply_units = 10
    base_price = 220.0
  }
  weather = @{ condition = "Rain"; temperature_c = 24.0 }
  traffic = @{ traffic_level = "Severe"; avg_speed_kmph = 8.0 }
  competitor = @{ competitor_price = 190.0 }
} | ConvertTo-Json -Depth 5

Invoke-RestMethod -Uri "http://127.0.0.1:8000/predict" `
  -Method Post -ContentType "application/json" -Body $body
```

The response contains `city`, `predicted_price`, and `features_used`. The returned price
depends on the locally trained model; it is a prediction from simulated labels. Check API
readiness with `Invoke-RestMethod http://127.0.0.1:8000/health`.

## Tests

```powershell
pytest tests/ -v
```

The current suite contains 60 tests. The API tests load the tracked model artifact;
tests do not require a running Kafka broker, Docker daemon, or Kubernetes cluster.

## MLflow and Drift Checks

View logged training runs with:

```powershell
mlflow ui --backend-store-uri sqlite:///mlflow.db
```

Then open `http://127.0.0.1:5000`. Training logs MAE, RMSE, and R²; exact values vary
between generated datasets. Drift check and retraining commands:

```powershell
python monitoring/drift_detector.py
python pipeline/retrain_pipeline.py
```

The standalone drift script compares the saved reference features with a newly generated
synthetic batch. The retraining script can also accept recent features when called from
Python; production feature ingestion is not wired to it automatically.

## Kafka (Optional)

Start the local services after training a model. Compose requires a local `.env` file
because it is listed under the API service's `env_file` setting; create an empty one if
you do not need overrides.

```powershell
if (!(Test-Path .env)) { New-Item -ItemType File .env }
docker compose up --build
```

In separate terminals, run the host producer and consumer:

```powershell
$env:PYTHONPATH = "$PWD;$PWD/src"
$env:KAFKA_BROKER_URL = "localhost:29092"
python src/kafka_producer.py
```

```powershell
$env:PYTHONPATH = "$PWD;$PWD/src"
$env:KAFKA_BROKER_URL = "localhost:29092"
python src/kafka_consumer.py
```

The producer publishes order, weather, traffic, and competitor events to separate topics.
The consumer buffers by city and logs a record after all four arrive; this demo does not
send the record to `/predict`.

## DVC and Kubernetes

DVC defines the training stage and tracks the model/reference outputs. Configure a DVC
remote before using `dvc push` or `dvc pull`; see [dvc_SETUP.md](dvc_SETUP.md).

```powershell
dvc repro
dvc status
```

The `k8s/` manifests deploy the API. Build and publish the image, configure the required
registry/Kubernetes secrets and cluster, then apply the manifests with
`kubectl apply -f k8s/`. The GitHub Actions deployment job performs this only for pushes
to `main`.

## Limitations

- Synthetic labels are a placeholder; replace them with real historical price outcomes
  before drawing business conclusions from accuracy metrics.
- Kafka event assembly is not connected to feature engineering or the REST prediction
  endpoint. There is no built-in Kafka throughput or end-to-end latency measurement.
- API predictions are logged to local SQLite, but there is no Prometheus exporter or
  production monitoring dashboard.
- A real cloud DVC remote and live Kubernetes deployment require environment-specific
  credentials and have not been verified by this repository's local commands.
